## Resumen ejecutivo

**El repositorio NO está vacío.** En el árbol de `main` se observan 704 entradas (497 archivos y 207 directorios), aproximadamente 493.642 bytes de contenido de archivos versionados según el árbol consultado. Contiene una base de Unreal Engine, un proyecto Unity separado, scripts de automatización, pruebas, documentación y un runtime auxiliar Cloudflare.

La prioridad no es crear un videojuego desde cero ni reemplazar el trabajo existente: es reducir la ambigüedad de arquitectura, automatizar validaciones en GitHub y verificar los motores con sus herramientas reales antes de afirmar que compilan.

## Controles automatizados que sí se pueden realizar en GitHub

El workflow añadido en esta rama valida:
1. pruebas Python ya existentes;
2. presencia y coherencia básica del proyecto Unity;
3. parseo de JSON versionados seleccionados;
4. integridad estructural de archivos clave.

No instala Unreal Engine ni Unity, no consume licencias y no publica despliegues. Si falla una prueba existente, se debe corregir el fallo real y no desactivar el control.

## Bloqueadores para cerrar la auditoría

- **B1 — Decisión de motor:** confirmar cuál será el motor de producción. No migrar ni borrar carpetas hasta tomar esa decisión.
- **B2 — Compilación Unreal:** ejecutar build/automation con Unreal Engine 5.8 real.
- **B3 — Compilación Unity:** abrir/importar con Unity `6000.3.0f1`, ejecutar validación y build Linux; no inferir éxito a partir del script.
- **B4 — Runner:** confirmar contacto reciente del runner y resultado del job; un servicio local activo no prueba que GitLab acepte trabajos.
- **B5 — Gameplay:** comprobar movimiento, cámara, combate, interacción, Nexo, progresión, guardado/carga y derrota/respawn en una ejecución real.
- **B6 — Arte:** inventariar assets reales, licencias, tamaños y referencias rotas; las carpetas de destino no equivalen a contenido terminado.
- **B7 — Seguridad:** escaneo de secretos/dependencias y revisión de permisos de repositorio y workflows.
- **B8 — Release:** producir un build reproducible, registrar versión/commit, artefacto y resultado de lanzamiento.

## Criterio de aceptación

La auditoría se considerará cerrada solo cuando haya: motor maestro declarado; CI verde; compilación real del motor elegido; pruebas de gameplay ejecutadas; build Linux que arranque; revisión de secretos y dependencias; y una release vinculada al commit exacto. Hasta entonces, el estado correcto es **base de desarrollo existente; finalización y compilación real pendientes de evidencia**.
